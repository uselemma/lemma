An **issue** is a durable, grouped failure pattern inferred from trace evidence. Lemma observed the issue in one or more traces.

Lemma does not require you to write assertions. After a conversation goes quiet (or immediately if there is no thread id), it analyzes traces for behavior that materially hurt the agent's task, then groups repeated evidence. **Detection and grouping are probabilistic.** Always open supporting traces before you treat a title as a confirmed bug.

Lemma does not currently ship standalone monitors or incidents. Alerting follows this issue lifecycle ([Slack](/connections/slack) and [webhooks](/connections/webhooks)).

## Issues and supporting traces

- One issue, many supporting traces.
- Opening an issue shows rationale, category, priority signals, linked traces, and actions.
- Opening a trace shows whether Lemma observed one or more issues in that run.

## Status

| Status | Meaning |
| -- | -- |
| `open` | Active; not being worked |
| `in_progress` | Active; someone is working it |
| `resolved` | Terminal: you believe the underlying defect is fixed |
| `dismissed` | Terminal: not a real problem, or not worth tracking |

`resolved` and `dismissed` are mutually exclusive. The transition that commits first wins if two people act at once.

**Reopen:** matching evidence may reopen a **resolved** issue. Matching evidence **does not** reopen a **dismissed** issue. Manual reopen does not by itself change a linked Linear ticket (see [Linear](/connections/linear)).

You can flag for review, assign a Lemma member, and add tags. Assignment in Lemma does not write to Linear unless you create a ticket and choose combined assignment.

## Priority and grouping

Priority is derived from recurrence and impact across the population of issues (for example volume and spikes), not from a monitor threshold you configure. Treat it as a triage hint.

Grouping aims at one issue per underlying defect. If two issues look like the same bug, inspect the supporting traces rather than assuming a missed merge; grouping can be revised as more traces arrive.

## Investigating

1. Filter the issues table (status, agent, assignee, flagged, search).
2. Open the issue and read why it was flagged.
3. Open supporting traces (conversation + execution tree).
4. Ask [Inspect](/platform/inspect) on the issue: why it fired, scenarios, likely cause, how to fix.
5. Export markdown (`GET /issues/{id}/markdown` or the UI equivalent) for a ticket or coding agent.
6. Resolve or dismiss, optionally with feedback so future extraction can learn from false positives.

## Workflow connections

- **[Slack](/connections/slack)** — issue alerts and Issue Briefs to a project channel.
- **[Linear](/connections/linear)** — optional one-to-one ticket link; create, exact-link, or unlink explicitly.
- **[Lemma MCP](/connections/mcp)** — coding agents list and act on issues with an organization API key.
- **[Webhooks](/connections/webhooks)** — `issue.created`, `issue.resolved`, `issue.dismissed`, `issue.reopened`.

Connecting Slack or Linear never auto-creates tickets. Recurrence does not create a new Linear ticket.
