`npx @uselemma/setup` connects an app and its coding agent to Lemma through one browser approval. Your coding agent runs it when it follows the `lemma-setup` skill from the setup prompt in Lemma. This page lists the two commands, their flags, what they write for each coding agent, when an existing key is reused, and the exit codes.

## Start, then wait

Setup runs as two commands, so neither one outlasts a coding agent’s default command timeout. Run both from the app’s root directory, where the app loads `.env`:

1. `start` checks every file it will write, starts the approval, prints the approval URL and a code, opens the browser, and returns at once
2. `wait` checks for the approval for up to 90s. While the approval is pending it exits with `5`; run it again. Once you approve, it writes the keys and exits with `0`

```bash
npx --yes @uselemma/setup@0.1.0 start \
  --harness claude-code \
  --project-name "Support bot" \
  --agent-name support-bot \
  --org acme-inc-x1y2
npx --yes @uselemma/setup@0.1.0 wait
```

Between the two, `start` keeps the approval in a file under `~/.lemma/setup/pending/` that only you can read, one per app directory. `wait` deletes it once the approval ends. The approval code expires 10 minutes after `start`. Both commands need Node.js 20 or later.

## Flags for start

The coding agent passes the names it inferred from the codebase. You confirm or edit both names on the approval page:

| Flag | Required | Value |
| --- | --- | --- |
| `--harness` | Yes | The coding agent: `claude-code`, `cursor`, `codex`, `opencode`, `pi`, `hermes`, `openclaw`, or `other` for any other agent |
| `--project-name` | Yes | The proposed project name, up to 200 characters |
| `--agent-name` | Yes | The proposed agent name, the root trace `name`. Lemma stores it in lowercase with dashes, for example `support-bot`. `trace` isn’t allowed |
| `--org` | No | The organization’s slug from the setup prompt, for example `acme-inc-x1y2`. The approval page selects that organization when you belong to it, and then offers no **Switch organization** link. To choose another organization, run `start` again without `--org` |
| `--repository` | No | The repository, for example `acme/support-bot`. The command removes credentials from a URL before sending it |
| `--framework` | No | The agent framework, for example `vercel-ai` or `langgraph` |
| `--api-url` | No | The Lemma API. Defaults to `https://api.uselemma.ai`. The command accepts HTTP only for `localhost` |
| `--no-browser` | No | Print the approval URL without opening a browser |

`wait` takes no flags.

## What one approval creates

An owner or admin of your Lemma organization approves the request on the page `start` opens, after choosing a plan if the organization has none. The approval creates the project, or uses an existing project you pick, and `wait` then receives each new key once:

- **Ingest key**: limited to the project. It can only send traces, so a leaked copy can’t read your data or write to another project
- **Admin key**: organization-wide, for the Lemma Model Context Protocol (MCP) server in your coding agent

Each key is named for the coding agent and the day, for example `Setup: Claude Code, Nov 18`. Find and revoke earlier ones under **Developer → API keys** in your organization settings.

## Files written to the app directory

`wait` writes two files in the directory it runs in. `start` checks both before the approval begins, and `wait` checks them again before it polls. Each says what it will skip or save elsewhere:

- **`.env`**: sets `LEMMA_API_KEY` and `LEMMA_PROJECT_ID`. A new file is readable only by you. In an existing file, other lines, `export` prefixes, and the file’s permissions stay as they are; the command warns when the file’s group or other users can read it. Setup never writes through a symlinked `.env` or replaces one that isn’t a regular file: `start` and `wait` say so, and `wait` saves both values to a file in `~/.lemma/setup/` that only you can read
- **`.env.example`**: adds empty `LEMMA_API_KEY=` and `LEMMA_PROJECT_ID=` lines, and creates the file if it’s missing. A `.env.example` that is a symlink or isn’t a regular file stays unchanged, and `start` and `wait` say so. A failed write is reported and never fails setup

If git doesn’t ignore `.env`, the command prints a warning. Add `.env` to `.gitignore` before you commit.

Lemma returns each new key once, so `wait` never drops one. When `.env` can’t take the ingest key although neither `start` nor `wait` found anything wrong before polling, `wait` saves `LEMMA_API_KEY` and `LEMMA_PROJECT_ID` to that private file, says where, finishes the other steps, and exits with `1`. Copy both values where the app loads its environment, then delete that file.

## Where the admin key goes for each coding agent

The admin key goes into your coding agent’s user-level MCP config as a server named `lemma`, pointing at `https://api.uselemma.ai/mcp/`. Setup replaces an existing `lemma` entry and leaves other servers and settings as they are:

| Coding agent | Where setup writes the `lemma` server | How to load it |
| --- | --- | --- |
| Claude Code | `claude mcp add-json lemma '<entry>' --scope local`, run from the repository root, so the key stays in your Claude Code config for this project and out of the repository | `/mcp`, or restart |
| Cursor | `~/.cursor/mcp.json`, under `mcpServers` | Reload MCP servers in Settings |
| Codex | A `[mcp_servers.lemma]` table with `http_headers` in `config.toml` under `CODEX_HOME` (default `~/.codex`) | Start a new session |
| OpenCode | `opencode.json` in `~/.config/opencode` (or `OPENCODE_CONFIG_DIR`), under `mcp.servers` when the file already uses it, otherwise under `mcp` | Restart OpenCode |
| Pi | `~/.pi/agent/mcp.json`, under `mcpServers` | `/reload` |
| Hermes | `config.yaml` under `HERMES_HOME` (default `~/.hermes`), under `mcp_servers`. Comments stay as they are | `/reload-mcp` |
| OpenClaw | `~/.openclaw/openclaw.json` (or `OPENCLAW_CONFIG_PATH`), under `mcp.servers` with the `streamable-http` transport | The gateway applies it; restart it if the tools don’t appear |
| Any other agent | A file in `~/.lemma/setup/` named for the app and the agent, readable only by you | Add the entry to your agent’s MCP config, then delete the file |

A new config file is readable only by you. Setup never changes an existing config’s permissions. When the file’s group or other users can read it, the command prints one warning that names the file and the `chmod 600` command to run.

When a config is a symlink, has contents setup can’t edit safely (for example a JSON5 file with comments, or a Codex `lemma` server written inline instead of as a `[mcp_servers.lemma]` table), or the `claude` command isn’t on your `PATH`, `start` says why and that the entry will go to the private file. `wait` says so too before it polls, including for a config that changed after `start`, then saves the entry there and exits with `0`. When an MCP write fails after approval instead (for example the config’s directory isn’t writable, the file changed while `wait` was polling, or Claude Code refuses the new server), `wait` saves the entry to the private file, so the admin key is never lost, and exits with `1`. The private file holds the entry in the agent’s own config format (TOML for Codex, YAML for Hermes, JSON for the others), ready to paste. For Claude Code it holds the bare `lemma` entry, `{ "type": "http", "url": …, "headers": … }`, as `claude mcp add-json` takes it. Each app gets its own private file, so setup in a second app never overwrites a key you haven’t copied yet. The command prints the entry’s shape, never the key.

For Claude Code, `start` reads the project’s local `lemma` entry. Without one, `wait` adds the server once, and if Claude Code refuses, saves the key to the private file without removing anything. With one, `wait` removes it and adds the new server; if that add fails, it restores the old entry and saves the new key to the private file. If Claude Code refuses the removal, the old entry stays as it is, and the new key goes to the private file.

Add Claude Code’s private entry to the same local scope, not the committed `.mcp.json`. Setup prints this command with the paths filled in and quoted for the shell. It reads the key from the file, so the key never appears in your shell history, and every step waits on that read: running it again after the file is gone changes nothing. Like setup, it then removes any `lemma` server in that scope, adds the entry with the same `claude mcp add-json` command setup runs, and deletes the private file once the add succeeds. It runs in a subshell, so your shell stays in its directory:

```bash
(cd '<repository root>' && entry="$(cat '<private file>')" && { claude mcp remove lemma --scope local >/dev/null 2>&1; claude mcp add-json lemma "$entry" --scope local; } && rm '<private file>')
```

Without the `claude` command, add the entry as `projects["<repository root>"].mcpServers.lemma` in `~/.claude.json` (or `.claude.json` in `CLAUDE_CONFIG_DIR`), with Claude Code closed, then delete the private file.

## When an existing key is reused

A re-run reuses a key only when Lemma confirms what it’s allowed to do. `start` asks Lemma’s `GET /auth/key` about each existing key before the approval begins:

- **Ingest key in `.env`**: kept when Lemma confirms an `ingest` key limited to the project in `LEMMA_PROJECT_ID`, and you approve that same project. Any other key, including a read or admin key for that project, gets a new ingest key, and `wait` replaces both values in `.env`
- **Admin key in the MCP config**: kept when Lemma confirms an admin key that isn’t limited to one project, and you approve in that key’s organization. Otherwise Lemma creates a new admin key, and `wait` replaces the `lemma` entry

A key Lemma rejects, or an answer that doesn’t arrive, counts as unconfirmed.

## Exit codes

The `lemma-setup` skill uses the exit code to decide the next step:

| Code | Command | Meaning |
| --- | --- | --- |
| `0` | `start`, `wait` | `start`: the approval started. `wait`: approved, and each key is written, kept, or saved to a private file that `start`, or `wait` before it polled, announced; the output names that file and includes `Project ID:` and `Agent name:` |
| `5` | `wait` | The approval is still pending. Run `wait` again |
| `1` | `start`, `wait` | Setup failed. The message says why, for example no pending setup in this directory, or no coding-agent setup on this Lemma environment. After approval, `wait` also exits with `1` when a key went to a private file because a write failed, or no key was saved; it finishes every other step first |
| `2` | `start`, `wait` | A command or flag is missing or invalid |
| `3` | `wait` | The approval code expired. Run `start` again |
| `4` | `wait` | The approver canceled, or is no longer an owner or admin. Run `start` again |

While a Lemma environment doesn’t offer coding-agent setup yet, its setup endpoints answer 404. `start` and `wait` then print one line saying so and exit with `1` without writing anything. Use [manual setup](/tracing/instrumentation/setup#set-up-manually) instead.

The commands never print a key or the device code. The approval code they print is the one the browser page shows, so you can match the two.

## The lemma-setup skill

The setup prompt in Lemma tells your coding agent to fetch and follow [`skills/lemma-setup/SKILL.md`](https://github.com/uselemma/lemma/blob/main/skills/lemma-setup/SKILL.md). The skill runs these steps in order:

1. Infer the project name, agent name, framework, and repository from the codebase, and read the organization slug from the prompt
2. Ask the Approach question (which integration path) and the Scope question (which agent paths), before any code changes
3. Run `start`, show you the approval URL and code, then run `wait` until it exits with `0`
4. Instrument the agent with the `lemma-tracing` skill, using the approved agent name as the root trace `name`
5. Send a first trace, after you agree to run the agent
6. Load the Lemma MCP server and record the agent’s context with the `lemma-artifacts` skill
7. Report the files it changed and the build or deploy steps that need attention, such as adding both variables to your deployment’s secrets
